# Unified items/tasks design

**Status: fully rolled out.** Implemented, tested (139/139
`tst/*.bats`), migrated against the live `bensiv-notes.db`/vault, and
`/usr/local/bin/brex` replaced with the new build. See "Live rollout"
at the end for exactly what that involved -- it surfaced three real
bugs no amount of synthetic testing had caught.

## Goal

Collapse `notes` and `tasks` into one shared knowledge pool, with
task-specific fields pulled into their own companion table joined by
id, and "ongoing comments" implemented as the existing note-append
mechanism rather than a new subsystem. Tasks and notes are
cross-linkable (`connections`) and browsable interchangeably; `task
list` shows short titles again because `content` is no longer where a
task's whole history lives.

This does *not* adopt daat as a backend (ruled out: no vault/markdown
sync exists there today, and the Obsidian-editable `bensiv-notes/`
vault is load-bearing). It borrows one principle from daat's
`schema.md` -- "a [feature] never becomes a column on the entity's own
table, it gets its own companion table instead" -- applied to the new
tracking table the same way daat applies it to multivalue fields.

## Naming: the companion table is called `tasks`

Not `task_meta`. There's no other table competing for that name (the
pre-unification flat table is renamed to `tasks_legacy_backup` during
migration, never left in place), and this table holds real operative
fields, not secondary bookkeeping -- `tasks` is just the plain,
correct name once nothing else needs it. `notes` keeps its own name
too, for the same "why touch a label for zero behavioral benefit"
reasoning.

**The one real wrinkle this naming choice creates**: the schema-init
path (`sql_schema.sql_init`) creates `tasks` via `CREATE TABLE IF NOT
EXISTS`, which silently no-ops if a brain still has the *old*,
flat-shape `tasks` table (its own `content`/`subject`/`comment`
columns) sitting under that exact name. Migration has to detect that
case and rename the old table out of the way *before* the new
tracking-only `tasks` table can be created at all -- see "Migration"
below for how `migrate_legacy_tasks` handles this (it's the one
non-obvious ordering dependency in the whole change).

## Schema

```sql
-- notes: the shared pool for both plain notes and tasks. Only change
-- from before: a real `id` column, generated by bx_utils.generate_id
-- the same way task ids always have been (a random 10-digit numeric
-- string, coerced to INTEGER by SQLite's column affinity) -- not
-- AUTOINCREMENT. This keeps the id *style* consistent with existing
-- task ids already referenced by number throughout old task content
-- ("see task 946045870"), and reuses generate_id's existing
-- table-scoped uniqueness check rather than introducing a second id
-- scheme.
CREATE TABLE IF NOT EXISTS notes (
    id INTEGER PRIMARY KEY,
    time TIMESTAMP DEFAULT (datetime('now', 'localtime')),
    subject TEXT,
    title TEXT,
    content TEXT,
    size INTEGER DEFAULT 0,
    UNIQUE (title, subject)
);

-- Operative/actionable fields only -- no content, no subject, no
-- title; those live solely on notes. A row's existence here is the
-- only "is this a task" signal -- no kind/type column, nothing that
-- can drift out of sync with itself. Promoting an existing note into
-- a task, or demoting one back to a plain note, is just
-- inserting/deleting a row here.
CREATE TABLE IF NOT EXISTS tasks (
    item_id INTEGER PRIMARY KEY REFERENCES notes(id),
    due_to TIMESTAMP,
    overdue INTEGER,
    done TIMESTAMP DEFAULT NULL,
    owner TEXT DEFAULT NULL,
    importance INTEGER DEFAULT 1,
    urgency INTEGER DEFAULT 1
);
```

`connections` is untouched -- already keyed on `(title, subject)`
pairs, so a task and a note can `[[wikilink]]` each other the moment
they share one identity space.

## Vault: one file per item, no separate `tasks/` tree

A task's file lives at exactly the same place a plain note's would --
`<vault>/<subject>/<title>.md` (or `<vault>/<title>.md` with no
subject) -- with extra frontmatter keys, plus one explicit
discriminator so the sync code knows to also touch `tasks`:

```
---
id: 494140529
title: Re-run the Advanced Validation backlog check
is_task: true
due_to: 2026-08-19 00:00:00
overdue: 0
done:
owner:
importance: 5
urgency: 4
time: 2026-08-19 00:45:10
---
initial body, if any

2026-08-20 09:14:11
Backlog check re-run: 340 failing records, mostly ...
```

**This was not the original plan and needed a real fix mid-implementation.**
The original idea was "task files keep living under their own
`tasks/<subject>/<id>.md` tree, just retarget the SQL." That's unsound
the moment a *plain, pre-existing* note gets promoted into a task
(`brex task add -s benchling -t "some finding" ...` on a note that
already has its own file at `benchling/some finding.md`): a second,
separate file under `tasks/` would start diverging from the original
note file the instant either one gets edited, since they'd both claim
to represent the same DB row's `content`. The only correct fix is one
file per item, at the note's own natural location -- which means the
generic vault sync path (`vault_to_sql.lua`, used for every plain note
today) has to become frontmatter-aware, since it previously had no
concept of frontmatter at all:

- `vault_to_sql.lua`'s `vault_to_sql()` now runs every file's raw
  content through `bx_utils.parse_frontmatter` before treating the
  result as `content` -- a strictly backward-compatible change, since
  `parse_frontmatter` is a no-op (empty metadata, body unchanged) on
  any file with no `---` block, which is every plain note today.
- If the parsed frontmatter has `is_task: true`, an upsert into
  `tasks` is appended to the same batched transaction, using the
  note's own id (freshly generated for a brand new file, reused as-is
  for an existing one).
- `update.lua`'s `update_note_from_file` (the single-file path behind
  `note edit` and `update --file`) got the identical treatment.
- `is_task` is a deliberate explicit flag, not inferred from "has a
  due_to" etc. -- a plain note that happens to pick up an `importance`
  field for unrelated reasons must never accidentally become a task on
  next sync.
- `update.lua`'s old `sync_tasks_from_vault` (a second, always-
  recursive walk over a dedicated `tasks/` tree) is deleted outright --
  the generic note-sync path now covers everything, one mechanism
  instead of two.

**A second real bug found only by testing**: `vault_to_sql`'s inserts
are batched into one transaction and committed at the very end, but
each new file's id was being generated via `bx_utils.generate_id`
mid-loop -- and `generate_id` reseeds `math.random` from `os.time()`
(1-second resolution) on *every call*. Two new files processed within
the same wall-clock second reseed to the identical value and draw the
identical "unique" id (unique only against the DB, which hasn't
committed anything from this batch yet) -- `brex update --force`
against a real vault (hundreds of files, easily several per second)
hit this reliably as a `UNIQUE constraint failed: notes.id`. Fixed
with a `next_note_id()` helper that tracks ids already claimed this
pass and, on a collision, redraws with a bare `math.random()` call
(advancing the already-seeded generator) rather than calling
`generate_id` again (which would reseed to the same value and loop
forever).

## Code changes by file (as implemented)

**`sql_schema.lua`** -- `notes` gains `id`; new `tasks` table. Both
`CREATE TABLE IF NOT EXISTS`, safe to re-run unconditionally.

**`task.lua`** -- most of the module, rewritten:

- `ensure_schema(brain_file)` -- runs `sql_schema.sql_init`, backfills
  `notes.id` for brains that predate the column
  (`ensure_notes_id_column`), then `migrate_legacy_tasks`. Called at
  the top of every `do_task` invocation, mirroring the old
  `ensure_priority_columns` pattern.
- `migrate_legacy_tasks(brain_file)` -- one-time, idempotent
  (gated on `sync_meta.tasks_migrated_to_notes`). Detects an old-shape
  `tasks` table by the presence of a `content` column (new-shape
  `tasks` never has one), and if found: renames it to
  `tasks_legacy_backup` *before* re-running `sql_init` (so the
  tracking-only `tasks` table can actually be created under that now-
  vacated name), then migrates each row -- `title` = old `content`
  (disambiguated with a trailing `[<id>]` on a genuine title
  collision, since a bare numeric task id was never subject to
  `notes`' `UNIQUE(title, subject)` before), `content` = `"DONE: " ..
  comment` if the row had one, `tasks.item_id` = the *original* task
  id (never reassigned -- old content elsewhere already refers to
  tasks by that number). Never drops the old table.
- `find_or_create_note` / `add_task` -- **find-or-create on `notes`,
  then upsert on `tasks`**, not an unconditional insert. Since a task
  is nothing but a `notes` row with a `tasks` row attached by id,
  "create a task" and "start tracking an existing note" are the same
  operation: `brex task add -s benchling -t "some finding" -e
  2026-09-01 -p 4` promotes an existing `benchling/some finding` note
  if one exists (appending any given `-c/--content` as a comment
  rather than overwriting it), creates one fresh otherwise. The
  `tasks` upsert uses SQLite's `ON CONFLICT(item_id) DO UPDATE`, so
  re-running `task add` against an already-tracked task just updates
  its tracking fields. No explicit transaction wrapping -- two plain
  sequential `database.sqlite_update` calls, matching how the rest of
  this codebase already treats note/task writes (e.g. `mark_done`'s
  separate `UPDATE` + `append_content` calls) rather than introducing
  a new pattern.
- `list_tasks` -- `SELECT notes.title, notes.subject, ... FROM notes
  JOIN tasks ON tasks.item_id = notes.id WHERE tasks.done IS NULL`;
  the rendered column is `title`, not `content`. Priority-quadrant
  math, color coding, and `task_columns` settings are unchanged,
  just reading off the joined row. The *default* column fallback (used
  when `settings.json` doesn't define `task_columns`) changed from
  `content` to `title`.
- `mark_done` -- `UPDATE tasks SET done = CURRENT_TIMESTAMP WHERE
  item_id = ?`, then if `--comment` was given, appends
  `"DONE: " .. comment` via `note.append_content`. There is no
  `comment` column any more -- the done-note is just the log's last
  entry.
- **new** `comment_task` -- `brex task comment --id <id> --comment
  "..."`: looks up `(subject, title)` for the id, appends a
  timestamped entry via `note.append_content`. This is "ongoing
  comments, not just at done time," and it's a thin wrapper because
  the append machinery already existed for notes.
- **new** `show_task` -- `brex task show --id <id>`: prints title,
  subject, priority, due date, done state, and the full `content` log.
  The "drill into one task" view, needed now that `list` only shows
  titles.
- `delay_due`, `update_priority`, `last_done` -- same shape as before,
  targeting `tasks`/`item_id` via the join instead of a flat table.
- `backup_task` (was `backup_tasks`) -- rewritten to read the
  `notes`/`tasks` join and write one file via `note.get_note_paths`
  (task.lua no longer has its own vault directory/path logic at all);
  `persist_task` keeps the same "single item, or full `sync.refresh`
  for a wildcard id" shape `persist_tasks` had.

**`note.lua`** -- `append_content`, `get_note_paths`, `note_exists`
added to the module's export table (`note.append_content` etc.) so
`task.lua` can call them explicitly rather than relying on this
codebase's implicit-global convention (every top-level function in a
required file is already a bare global once that file loads, but an
explicit `require("note")` + qualified call is less surprising to
read).

**`vault_to_sql.lua`** -- frontmatter-aware now (see "Vault" above);
new `task_upsert_sql`/`is_task_metadata` helpers, exported on the
module table since `update.lua`'s single-file sync path calls them
too. `next_note_id()` fixes the same-second id-collision bug.

**`update.lua`** -- `sync_tasks_from_vault` deleted; `update_from_vault`
no longer calls it (the generic note sync covers tasks now).
`update_note_from_file` parses frontmatter the same way and upserts
`tasks` when `is_task` is set. The legacy `tasks.tsv` import path
(`init.lua` and `update.lua` both had one) is **removed outright**,
not adapted -- its column shape (a flat tasks row, `comment` column
and all) has no mapping onto the new schema, and it was already marked
"deprecated and will be removed in a future release" in its own
comments. `--force` rebuild's `DROP TABLE` list now also drops `tasks`
and `tasks_legacy_backup`.

**`agent.lua`, `agent_engine.lua`, `agent_tools/bridge.lua`** -- each
had a raw query against the old flat `tasks`
(`agent_engine.process_tasks`, `bridge.dispatch`'s `task.list`) --
now joins `notes`+`tasks`. `agent.lua`'s own `ensure_owner_column`
now just delegates to `task.ensure_schema`.

**`knowledge_pool.lua`** -- untouched, deliberately. `sync_notes`'s
`FROM notes n` already covers tasks now that they're `notes` rows --
they're semantically searchable via `brex knowledge search` for free.
No exclusion filter: a task's content isn't different in kind from a
note's just because a `tasks` row also references it, and since any
note can be promoted into a task at any time, an exclusion filter
would make a note's search visibility change the instant someone
starts tracking it -- exactly the kind of accidental coupling this
design is trying to avoid.

**`help.lua`** -- `task`/`task add`/`task list`/`task done`/`task
delay` usage text updated for the new flags; new `task comment`/`task
show` entries; subcommand lists everywhere include `comment`, `show`.

**`init.lua`** -- default `settings.json` template's `task_columns`
changed from `content` to `title`; dead `task_file`/`tasks.tsv`
handling removed.

### CLI flags -- reconciled with `note.lua`

`argparse.lua`'s `def_args` requires exactly one short letter per
flag, no optional-short exceptions, so freeing `-t` for `--title` (to
match `note add`'s `-t/--title`) means `--due_to` needed a new letter:

```
-d --do          arg string false
-s --subject     arg string false   (unchanged)
-t --title       arg string false   (required; was --content's job)
-c --content     arg string false   (unchanged letter, now optional)
-e --due_to      arg string false   (was -t; freed since -t now means title)
-i --id          arg string false   (unchanged)
-m --comment     arg string false   (unchanged)
-n --number      arg string false   (unchanged)
-o --owner       arg string false   (unchanged)
-p --importance  arg string false   (unchanged)
-u --urgency     arg string false   (unchanged)
```

`add_task`'s error message changed from `"Must provide task content"`
to `"Must provide task title"`, matching `take_note`'s wording.

## Migration path implemented (`migrate_legacy_tasks`)

1. Additive schema (`notes.id`, new `tasks` table) plus the
   old-shape-detection/rename-first ordering described above under
   "Naming" -- both ship together, since the rename ordering is what
   makes the additive part actually land on an old brain.
2. Idempotent, gated on `sync_meta.tasks_migrated_to_notes`, runs from
   `ensure_schema` (called on every `task` command) -- no separate
   migration command to remember to run.
3. Verified end-to-end against a simulated old-shape brain (see test
   transcript below): original task ids preserved, done-comments
   folded into `notes.content` as `DONE: ...`, `tasks_legacy_backup`
   kept as a safety net, new `tasks` table correctly tracking-only.

```
--- notes ---
494140529|benchling|Legacy benchling task|
777000111|work|Legacy done task|DONE: wrapped up nicely
--- tasks (new shape) ---
494140529||5|4|
777000111||1|1|2026-01-01 10:00:00
--- tasks_legacy_backup preserved ---
2
```

## Live rollout

Backed up `bensiv-notes.db` and the vault directory first (checksummed
copies), then ran the new binary against the real brain. In order:

1. **DB migration.** `brex bensiv-notes task list` triggered
   `ensure_schema` -> `migrate_legacy_tasks` for real: 294 tasks moved
   into `notes`+`tasks`, original ids preserved, one genuine title
   collision (`benchling-schema`/"updating schema through api", two
   tasks) disambiguated automatically exactly as designed, old `tasks`
   renamed to `tasks_legacy_backup` (still there, untouched).
2. **`settings.json`** `task_columns` updated from `content` to
   `title`.
3. **Title-shortening pass**, 15 pending tasks whose title was still
   the full multi-sentence description (same manual editorial process
   as the description cleanup earlier this session, just landing in
   `title` now): e.g. task 494140529's ~650-character paragraph became
   "Re-run and clean up the Advanced Validation backlog now that the
   masking crash is fixed", with the full text preserved verbatim in
   `content`. `task list` now genuinely reads as one-liners.
4. **Replaced `/usr/local/bin/brex`** (confirmed stale -- an older
   build, separate from this repo's own `bin/brex`, and what this
   whole session had actually been running against) with the new
   binary, backed up first.

### Three real bugs found only by running this against live data

Synthetic tests (139/139 passing) never exercised any of these --
each needed either a real vault with hundreds of files, or a title
containing an ordinary English apostrophe, to surface.

1. **Vault files never moved, so the very first auto-resync tried to
   delete all 294 migrated tasks.** Every non-read-only `brex` command
   runs a full `sync.refresh` before dispatch (`brex.lua`,
   `is_read_only_command`); that resync treats any DB row with no
   matching vault file as deleted-from-vault and removes it. The DB
   side of the migration was done, but the vault files were still the
   *old* `tasks/<subject>/<id>.md` shape in a location the (one-level-
   only) generic walker never even looks at -- so all 294 rows read as
   "not in vault." Caught before any real deletion happened (a failed
   multi-statement transaction rolls back whole, verified by checking
   row counts were unchanged after the failure), but it took a
   temporary `BREX_SKIP_AUTOSYNC` env-gated escape hatch in `brex.lua`
   (added, used to write the 294 new-location vault files via
   `task prioritize` self-reapplies, then fully removed once real data
   confirmed clean) to get out of the chicken-and-egg spot: normal
   task commands couldn't run without the destructive auto-resync
   firing first, and the fix *was* running a task command.
2. **Titles containing `/` broke path construction outright** (`get_note_paths`
   built `.../Reconcile field type/naming inconsistencies.../....md`,
   a literal nested path) **and titles longer than a filename limit
   failed to write at all** (102 old *done*-task titles, never
   shortened since the editorial pass only covered the 25 pending
   ones, some past 2900 characters). Fixed `get_note_paths` to
   sanitize `/` to `-` (a note's filename is already its identity on
   next sync -- consistent with how every other note/task title is
   already derived from its filename); mechanically truncated the 102
   over-length titles to a safe length at a word boundary with an
   `[<id>]` disambiguator, moving the full original text into
   `content` exactly like the 15 manually-shortened pending tasks.
3. **`vault_to_sql.lua` interpolated titles/subjects into SQL with no
   escaping anywhere in the file** -- pre-existing, not introduced by
   this change, but only ever exercised by note titles that happened
   to contain a `'`. Migrated task titles are ordinary English prose
   ("the ledger's update", "job's integrity report"), so this broke on
   the very first real resync of the live vault (a huge batched
   multi-statement transaction, one bad statement corrupts the whole
   thing, surfacing as a confusing "syntax error near 'retrieval'" --
   the parser choking on unrelated text elsewhere in the batch after
   an earlier unescaped apostrophe closed a string literal early).
   Fixed every interpolation site in that file to go through
   `database.escape_sqlite` -- consolidated onto that one existing,
   canonical function (`database.lua` already exported it) rather than
   keeping a second local reimplementation, per a mid-session
   suggestion to prefer one upstream escaping path over scattering
   calls at each site. A fully "upstream" fix (relying on
   `database.sqlite_update`'s own built-in varargs-based escaping
   everywhere, the way `knowledge_pool.lua` already does) would need
   this file's batched multi-statement transaction restructured into
   one flattened template+args call across potentially hundreds of
   statements -- judged too risky to attempt against live data
   mid-migration; worth doing as a deliberate follow-up, not a rushed
   one.

One stray mid-migration artifact left in place, flagged rather than
silently removed: task 494140529 has a verification comment appended
("Verified: unified notes+tasks migration completed and vault fully
resynced.") from the final live end-to-end check.
